# Чистка комментариев и докстрингов

## Зачем это

Комментарий живёт дольше, чем контекст, в котором он написан. Через полгода никого не
интересует, почему мы выбрали именно такое решение - интересует, что сломается, если этот
код тронуть. Скилл убирает первое и сохраняет второе.

Второй мотив приземлённее. В комментарии попадают символы, которые обычный человек не
наберёт с клавиатуры - длинное тире, ёлочки, стрелки. Дописать строку к такому комментарию
неудобно, и он начинает разъезжаться: половина через `—`, половина через `-`.

## Что делать

1. Собрать нарушения скриптом `scripts/scan_comments.py`.
2. Пройти по прозе руками - это работа на суждение, скриптом не делается.
3. Прогнать `scripts/normalize_chars.py` - механическая замена символов.
4. Проверить, что линтер и тесты зелёные.

```bash
python3 scripts/scan_comments.py            # что нарушено, с номерами строк
python3 scripts/normalize_chars.py          # покажет, что заменит
python3 scripts/normalize_chars.py --write  # заменит
```

Оба скрипта по умолчанию берут файлы, изменённые в ветке относительно `develop`. Ветку или
базовый коммит можно задать аргументом, отдельные файлы тоже принимаются.

Сканер не только ищет символы и пунктуацию - он ловит докстринги в повелительном наклонении
и шапки модулей. Прогнать его стоит и в конце, после ручной правки: пропущенные докстринги
находятся именно так.

После любой правки списков символов запускать `python3 scripts/selfcheck.py`. Он проверяет
главное - что замена не залезает в строковые литералы кода. Эта ошибка уже случалась и
портила код молча, без падения.

## Правила

### Голос

Докстринг описывает, что делает функция, в третьем лице настоящего времени.

```
Создать хранилище        ->  Создаёт хранилище
Забрать сегменты трасс   ->  Забирает сегменты трасс
Убрать витки за сутки    ->  Убирает витки за прошедшие сутки
```

Половинчатость хуже любого из двух вариантов. Если в файле часть докстрингов в
повелительном наклонении, а часть в третьем лице, читатель начинает искать смысл в этой
разнице, а его нет.

### Что остаётся, а что уходит

Это самое тонкое место, и здесь скрипт не поможет.

**Остаётся** то, что нельзя вывести из кода и что предупреждает о последствиях правки:

- поведение внешней системы, которое выглядит нелогично. *"На битый токен платформа
  отвечает 401 и пустотой, а гостю отдаёт всё"* - без этого следующий разработчик уберёт
  откат в гостя как лишний;
- неочевидные свойства данных. *"Номера витков уникальны только внутри аппарата"* -
  объясняет составной ключ, который иначе выглядит избыточным;
- ограничения, о которые уже спотыкались. *"Правая граница не включается, from=X&to=X
  отдаёт пустоту"* - защищает `+1`, который читается как ошибка на единицу.

**Уходит** всё, что описывает нас, а не код:

- почему выбрали этот вариант, какие рассматривали, чем плох соседний;
- история задачи, номера тикетов, "раньше здесь было";
- пересказ кода словами: `# увеличиваем счётчик` над `count += 1`;
- рассуждения о будущем: "потом переделаем", "когда появится X".

Граница проходит так: **комментарий про внешний мир остаётся, комментарий про наши
решения уходит**. Историю решений хранит git и проектная документация, а рядом с кодом
она только мешает.

### Место комментария

Предупреждение стоит рядом с кодом, который защищает, а не в шапке файла. Комментарий в
заголовке за шестьдесят строк от опасного места не спасёт того, кто правит именно это
место.

```python
# было: в шапке модуля
"""
...линия рвётся там, где конец кусочка не совпал с началом следующего...
"""

# стало: у самой проверки
for segment in segments:
    # Дыра в цепочке - это 180-й меридиан. Пересекающий его сегмент платформа
    # выбрасывает. Сшить концы напрямую - протянуть линию через полмира.
    if line and line[-1] != segment.start:
```

### Шапки модулей

Убираются целиком. Предметные факты из них переезжают либо к соответствующему коду по
правилу выше, либо в проектную документацию.

Перед удалением проверить, что линтер не требует докстринг модуля: в `pyproject.toml`
коды `D100` и `D104` должны быть в `ignore`. Если их там нет, это решение пользователя -
спросить, добавлять ли их в игнор.

### Пунктуация

**Точка с запятой не используется.** Заменяется на точку или на конструкцию с запятой.

```
Разбирает фичу в сегмент; бросает ошибку   ->  Разбирает фичу в сегмент, бросает ошибку
Прототип-креды; в проде переопределить     ->  Прототип-креды, в проде переопределить
```

**Двоеточие только перед настоящим списком.** «Продукты: 1. Яйцо 2. Молоко» - можно.
Двоеточие, вводящее пояснение, заменяется на тире или на запятую.

```
Ключ составной: номера уникальны внутри аппарата
  ->  Ключ составной - номера уникальны внутри аппарата

Граница - начало суток, а не "сейчас": иначе витки исчезнут к обеду
  ->  Граница - начало суток, а не "сейчас". Иначе витки исчезнут к обеду
```

Тире годится, когда двоеточие вводило пояснение к одному понятию. Когда после двоеточия
шло целое самостоятельное утверждение, лучше разбить на два предложения - запятая в таком
месте склеивает то, что склеивать не стоит.

Двоеточия внутри технических записей не трогаются - это не проза:

```
EPSG:4326   orbits:zorkiy_tracks   http://...   00:00   # noqa: SLF001   {'ключ': 1}
```

### Символы

Заменяются на то, что набирается с обычной клавиатуры.

| Было | Стало | Почему |
|---|---|---|
| `—` длинное тире | `-` | не набирается без спецсочетаний |
| `–` среднее тире | `-` | то же |
| `«` `»` ёлочки | `"` | то же |
| `"` `"` `'` `'` кавычки-запятые | `"` `'` | приезжают из редакторов при копипасте |
| `…` многоточие | `...` | то же |
| `→` `←` `↔` стрелки | `->` `<-` `<->` | |
| `≤` `≥` `≠` | `<=` `>=` `!=` | |
| `²` `³` | `2` `3` или словом | `км²` -> `кв. км` |
| `₽` | `руб.` | |
| неразрывный пробел U+00A0 | обычный пробел | невидим, ломает выравнивание |

Что **не** трогается: буква `ё`, знак `№`, знак `°`. Первые два набираются с русской
раскладки, а `°` не имеет короткого аналога - писать «градусов» длиннее и хуже читается.
Если сомневаешься в символе, которого нет в таблице, спроси, а не решай молча.

Замена делается только внутри комментариев и докстрингов. В строковых литералах кода
символы могут быть данными - сообщением пользователю, разделителем, тестовым вектором -
и менять их нельзя. Скрипт `normalize_chars.py` это различает, ручной `sed` - нет.

## Чего не касаться

- **`.env.example` и подобные файлы-инструкции.** Их читает тот, кто настраивает стенд, и
  для него подробное объяснение - единственный источник. Правила про комментарии в коде на
  них не распространяются.
- **Код, который был в проекте до ветки.** Расширять чистку на чужие файлы значит тащить в
  ревью правки, к задаче не относящиеся. Если такие места нашлись - показать списком и
  предложить отдельным коммитом.
- **Проектную документацию** (`CLAUDE.md`, `README.md`). Это не комментарии.

## Попутные находки

Читая комментарии подряд, почти всегда находишь такие, которые **врут** - код изменился, а
текст остался. Врущий комментарий хуже отсутствующего: отсутствующий заставляет читать
код, врущий уводит в сторону.

Такие места чинить и **показывать пользователю отдельно** - это уже не стилистика, а
дефект. Пример из практики: докстринг утверждал «значение по умолчанию - `current`», хотя
в коде давно стояло `MINIMUM`.

## Как отдавать результат

Коммит не делать, если пользователь не попросил явно - сначала он смотрит дифф.

В отчёте показать:

- сколько строк комментариев и докстрингов было и стало;
- два-три примера «было -> стало», чтобы пользователь сверился со стилем;
- отдельно - врущие комментарии, если нашлись;
- отдельно - нарушения в коде, который был до ветки, с предложением сделать их потом.
