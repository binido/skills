# Change

Доведи порученное изменение до проверяемого результата. Этот скилл задаёт общий
процесс и границы задачи; методы диагностики, реализации, ревью и общения бери
из подходящих скиллов, если они доступны. Средства работы выбирай из текущего
окружения: конкретный агент, инструменты задач и хранилище памяти не требуются.

## 1. Определи результат и контекст

- Зафиксируй ожидаемое поведение и способ его проверить по запросу, тикету или
  замечаниям ревью. Уточняй только пробелы, от которых зависит результат и которые
  нельзя закрыть чтением проекта.
- Прочитай применимые инструкции проекта: `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`
  или их аналог в окружении. За архитектурными решениями и командами проверки
  обращайся к документации и конфигам проекта.
- При работе в Git проверь ветку, рабочее дерево и недавние изменения. Сохрани
  чужие незакоммиченные правки и учти уже сделанную часть задачи.
- Загрузи доступные записи о затронутой области: память, передачу контекста,
  глоссарий или ADR. Сверяй изменчивые сведения с текущим кодом и окружением.

Контекст достаточен, когда известны требуемое поведение, ограничения проекта
и способ проверки. Если разведку уже выполнил другой скилл в этой сессии,
используй её результаты; перечитывай при изменении файлов или нехватке сведений.

## 2. Подключи нужные специализации

Выбирай скиллы по их описаниям и условиям вызова. Примеры ниже — ориентиры,
а не обязательные зависимости; имя может отличаться или иметь префикс плагина.

| Потребность задачи | Подходящая специализация |
|---|---|
| Выбрать простое решение без лишних абстракций | `ponytail` |
| Воспроизвести дефект и установить причину | `diagnosing-bugs` |
| Разрабатывать через тесты, когда это запрошено или принято в проекте | `tdd` |
| Изменить интерфейс модуля или предметную модель | `codebase-design`, `domain-modeling` |
| Проверить HTTP-поведение на живом локальном сервисе | `verify-endpoint` |
| Применить правила стека, UI или комментариев | Профильные скиллы, например Vercel Skills или `comment-style` |
| Проверить готовый diff на требования и стандарты | `code-review` |
| Объяснить выбор, прогресс или результат | Open Steps, `i-have-adhd` |

Подключай только специализации, применимые к текущей задаче. Скиллы только
для ручного вызова используй лишь по запросу пользователя. Если пользователь
уже выбрал процесс реализации, дополни его правилами этого скилла вместо запуска
второго процесса. Инструкции пользователя имеют приоритет перед скиллами.

Если нужного скилла нет, выполни соответствующую работу доступными средствами.
Устанавливать зависимости ради этого процесса не требуется. За актуальными
сведениями о библиотеке обращайся к доступному источнику документации, например
Context7; для наблюдения за UI используй доступный браузерный инструмент.

### Объём тестов

Перед добавлением или изменением тестов прочитай [правила тестирования](references/testing.md).
Сначала найди существующее покрытие и назови ошибку поведения, которую поймает
новый сценарий. Расширяй подходящую проверку вместо дублирования. Положительные
и отрицательные сценарии держи в отдельных параметрических тестах.
Эти правила определяют объём и группировку проверок; скилл TDD определяет порядок
их написания. Не расширяй набор тестов только потому, что подключён скилл реализации.

## 3. Выполни изменение

До правок найди затронутый поток, вызывающие места и существующие проверки.
Для дефекта получи воспроизведение, способное отличить ошибку от исправленного
поведения. При недоступном окружении укажи ограничение и отдели гипотезу
от подтверждённой причины.

Кратко обозначь план и критерий готовности. Сложную работу разбивай на проверяемые
изменения поведения, учитывая зависимости, а не на обязательную задачу для каждого
файла. Веди план средствами окружения или коротким списком; уже согласованный план
используй повторно.

Продолжай в пределах порученной задачи. Согласование нужно при существенном
расширении объёма или действии за пределами полученного разрешения, а не из-за
количества затронутых файлов.

Вноси минимальные достаточные правки по конвенциям проекта. Проверяй результат
по ходу работы выбранным методом. Попутный рефакторинг и исправление старых
несвязанных ошибок вынеси за пределы задачи.

## 4. Проверь и передай результат

Запускай проверки через команды и обёртки проекта, если они предусмотрены.
Выбери проверки по изменённому поведению и риску регрессии; выполни также
обязательные проверки проекта. После успешного прогона повторяй их при новых
правках или появлении оснований сомневаться в результате.

Результат готов, когда требования выполнены и проверки это подтверждают.
Недоступную или неуспешную проверку обозначь явно: чтение кода и мысленный
сценарий не заменяют наблюдаемого результата. Если подключён скилл ревью,
используй его выводы для завершения проверки.

Новые устойчивые знания — ограничение, правило бизнеса, решение с неочевидной
причиной — сохрани в принятом проектом месте. Отчёт о сессии передай скиллу,
который уже отвечает за отчёты; второй отчёт не создавай. Если хранилища нет,
достаточно указать существенное знание при передаче результата.

В итоговом ответе укажи, что изменилось, чем проверено и что осталось
непроверенным. Форму ответа бери из активных скиллов общения и предпочтений
пользователя. Коммит и push выполняй только по явной просьбе; готовность кода
сама по себе не даёт такого разрешения.
