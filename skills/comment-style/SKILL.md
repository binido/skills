# Комментарии и докстринги

Читатель - разработчик, который через полгода открыл файл и собирается его править. Ему
нужно знать, что сломается, если тронуть этот код. Каждый комментарий пишется для него,
коротко и простыми словами.

Область - только комментарии и докстринги, которые ты пишешь или меняешь в текущей задаче.

## Сколько писать

По умолчанию - одна строка. Вторая мысль появляется, только если без неё следующий
разработчик сломает код. Из всех причин остаётся одна - последствие правки, одним
предложением через "Иначе ...". Всё, что объясняет ход наших рассуждений, остаётся в
сообщении коммита и описании MR.

```python
def cleanup_past(now: datetime) -> None:
    """Убирает записи за прошедшие сутки и старше."""
    # Граница - начало текущих суток, а не "сейчас". Иначе утренние записи исчезали бы
    # уже к обеду.
    boundary = now.replace(hour=0, minute=0, second=0, microsecond=0)
```

Предупреждение живёт в комментарии вплотную к строке, которую защищает. Докстринг остаётся
однострочным, а объяснение переезжает к коду.

## Когда нужен комментарий

Комментарий несёт факт, которого нет в коде:

- поведение внешней системы, которое выглядит нелогично. *"Правая граница у платформы не
  включается, from_date=X&to_date=X отдаёт пустоту."*
- неочевидное свойство данных. *"Ключ составной - номера заказов уникальны только внутри
  магазина, у двух соседних магазинов за день совпадают все 15 из 15."*
- ограничение порядка или окружения. *"Схема первой, создать таблицу в несуществующей
  схеме база не даст."*

Замеренные числа остаются как есть: "на 8-й странице обрезок, на 9-й пусто", "падает 26 запросов
из 75". Они убеждают лучше слов.

Всё остальное говорит сам код через имена. Код без комментариев - нормальное состояние.
Если комментарий объясняет непонятное имя, переименуй.

## Докстринги

Там, где у языка есть формат документации: Python `"""..."""`, JS/TS и Java/Kotlin `/** */`,
Rust и C# `///`, Go - комментарий над объявлением. Каждая функция, метод и класс получает
докстринг, если в проекте так принято или этого требует линтер. Иначе - только там, где
назначение не видно из имени.

Первая строка - одно предложение с точкой. Форма зависит от того, что описывается:

| Что | Форма | Пример |
|---|---|---|
| функция, метод | глагол в третьем лице | `Создаёт заявку по образцу существующей.` |
| класс, модель, сериализатор | существительное | `Справочник статусов заявок.` `Тело запроса экспорта заявок оператором.` |
| свойство, поле | существительное | `Статус заявки.` `Размер файла в байтах.` |
| тест | ожидаемое поведение как факт | `Пользователь видит только свои заявки в списке.` `Повторное прочтение не ошибка.` |
| класс с тестами | "Тесты ..." | `Тесты доступа для роли оператора.` |

- В Go строка начинается с имени: `// Parse разбирает строку в сегмент.`
- Возвращаемое особое значение - отдельным предложением: `Возвращает None, если объект
  пропал из бакета.`
- Перечисление правил - списком через `-` после двоеточия:

  ```python
  """
  Пароль по ТЗ:
  - 8-72 символа
  - латиница в обоих регистрах
  - цифра
  """
  ```

- Параметры описываются именами и типами. Секции `Args:` / `Returns:` / `@param` пишутся,
  только если они уже есть в проекте или их требует линтер.
- Файл начинается с импортов и кода, в том числе в тестах. Докстринг модуля - одна строка
  и только по требованию линтера.

## Текст

- Язык - тот, на котором уже написаны комментарии в проекте. В новом проекте - русский.
- Как коллеге в чате: короткие предложения, "потому что", "т.к.", "чтобы". Рубленая фраза
  подходит, если смысл ясен: `# Схема первой, создать таблицу в несуществующей схеме база не даст.`
- Подписи к тестовым данным - короткая метка с маленькой буквы: `# короче 8`, `# нет заглавной`.
- Только символы с обычной клавиатуры: `-`, `"`, `'`, `...`, `->`, `<=`, `>=`, `!=`,
  обычный пробел. Буква `ё`, знаки `№` и `°` - тоже с клавиатуры, их можно.
- Мысль заканчивается точкой. Две мысли - два предложения или запятая.
- Пояснение к понятию - через тире: `Сессия здесь - не вход пользователя, а одно открытое окно.`
- Двоеточие - только перед настоящим списком и в технических записях (`EPSG:4326`,
  `http://`, `00:00`, `# noqa: E501`).
- Выделение - словами, обычным регистром.

## Проверка перед сдачей

Задача не закончена, пока каждый комментарий и докстринг, который ты добавил или изменил,
не прошёл все пункты. Непрошедший переписывается или удаляется.

1. Несёт факт, которого нет в коде. Пересказ строки ниже - удалить.
2. Сокращается вдвое без потери для того, кто будет править. Если да - сократить. Типичный
   результат:

   ```
   Забрать прогноз, при необходимости спускаясь до гостевого режима.

   Негодный токен сегодня ХУЖЕ его отсутствия: на него платформа отвечает 401 и пустотой,
   а гостю отдаёт всё (проверено). Поэтому любой отказ по токену заканчивается повтором
   без заголовка - иначе своя же авторизация обнулила бы сбор за сутки.
   ```
   ->
   ```
   Забирает прогноз, при необходимости спускаясь до гостевого режима.

   Негодный токен хуже его отсутствия - на него платформа отвечает 401 и пустотой, а гостю
   отдаёт всё. Поэтому любой отказ по токену заканчивается повтором без заголовка.
   ```

3. Описывает код и внешний мир, а не нас. Маркеры для переписывания: номер тикета,
   "теперь", "раньше", "пока", "позже", "когда переедет", "мы решили", "для надёжности",
   "(проверено)", "схема взята с", "заодно", "не по прихоти", "сознательно".
4. Говорит сразу по делу. Начала "Эта функция...", "Важно:", "Примечание:", "NOTE:" -
   убрать, оставить само утверждение.
5. Форма первой строки совпадает с таблицей выше.
6. Символы - с клавиатуры, без `;`, без слов капсом, двоеточие только перед списком.
7. Не противоречит коду рядом. Если по пути нашёлся старый комментарий, который врёт, -
   исправить и отдельно сказать об этом пользователю.
