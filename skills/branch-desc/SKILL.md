# /branch-desc - описание ветки для MR

Аргументы: `$ARGUMENTS` - базовая ветка. По умолчанию основная ветка репозитория
(`main`/`master`/`develop`, смотри `git branch -a` или `CLAUDE.md`).

Читатель - коллега на ревью и тот, кто через месяц ищет, где сломалось. Ему нужно знать,
что поменялось по смыслу и что может ударить по соседям. Пересказ диффа ему не нужен.

## Алгоритм

1. Собери коммиты и статистику:
   ```bash
   git log <base>..HEAD --no-merges --format='%s'
   git diff <base>...HEAD --stat
   ```
   Коммиты `ci: release ...` и прочие автоматические не считаются.

2. Разложи коммиты по задачам. Номер задачи - токен вида `ABC-123` в сообщении коммита.
   - Ни в одном коммите номера нет - ветка делала одну задачу, описание одним списком.
   - Номера есть - каждая задача получает свой блок, даже если ветка названа по одной.
     Коммиты без номера относятся к задаче из имени ветки. Если в имени ветки номера нет,
     они уходят в последний блок `Прочее`.

3. Загляни в ключевые файлы, чтобы понять смысл: модели, сервисы, ручки, миграции, фоновые
   задачи. Читай только то, без чего непонятно, что поменялось.

4. Отбери пункты (ниже), напиши заголовок и описание, отдай пользователю одним блоком кода.

## Что попадает в список

Отдельный пункт получает:
- новая возможность, которую заметит пользователь или соседний сервис
- ломающее изменение - удалённое или переименованное поле, ручка, команда, файл, роль,
  другой формат ответа, другая логика доступа. Пишется прямо, что было и что стало:
  `source_id удален, его значение теперь в id`
- смена поведения, которую не угадать по названию задачи

Мелочь в пункты не дробится. Правки линтера, типизации, тестов, доки, переименования и мелкие
фиксы собираются в одну общую строку или опускаются:
`Прогнан ruff + mypy, поправлено все, на что ругались`, `Декомпозированы тесты сокетов`.

Пункт говорит, что поменялось, а не как это устроено. Реализация видна в диффе, в описание
она не идет:
- адреса и пути API, значения параметров, маппинг статусов, лимиты
- имена переменных окружения и настроек. Исключение - без них сервис не поднимется на
  стенде, тогда одна строка: `Для X нужны новые ключи в .env`
- примеры ошибок, коды ответов, названия библиотек и протоколов внутри фичи
- тесты и README, которые идут вместе с фичей

Одна фича - одна строка до ~80 символов. Вложенный список - только если у фичи есть отдельные
заметные снаружи изменения поведения, как в примере с уведомлениями ниже. Из чего фича
состоит (создание, пуллинг, скачивание), не перечисляется: `Реализована интеграция с X`.

Обычно выходит 2-6 пунктов на задачу. Больше 8 - значит мелочь не собрана или пролезла
реализация.

Слишком подробно:

```
- Добавлен провайдер X (REST API, вход через OAuth на `/auth`)
  - Заказ уходит с `priority: high`, окно доставки X выбирает сам
  - id заказа уходит в `external_ref`, повтор не создает дубль
- Добавлен пуллинг статусов X по `X_POLL_CRON`, `done` и `closed` считаются готовыми
- Накладная X скачивается по presigned-ссылке, дальше общий путь в бакет
- В текст ошибки поставщика добавлено тело ответа (например `NO_SLOTS`)
- Новые ключи окружения `X_API_URL`, `X_USERNAME`, `X_PASSWORD`, `X_POLL_CRON`
- Тесты на клиент, провайдер и скачивание X, обновлен README
```

Как надо:

```
- Реализована интеграция с X
- В ошибке поставщика теперь видна причина отказа
```

## Как писать

- Каждый пункт с `- `, без точки в конце.
- Прошедшее время, страдательный залог, глагол первым: `Добавлен`, `Удалена`, `Вынесена`,
  `Доработан`, `Исправлена`, `Переведены`. Для крупной переделки подходит существительное:
  `Переработка импорта на интеракторы`.
- Коротко, как коллеге в чате. Связки `+`, `/`, `теперь`, `больше не`, `только если`
  нормальны: `Назначить исполнителя можно только NEW заказу`.
- Уточнение или оговорка - в скобках, своими словами:
  `(пока сохранен старый вывод)`, `(это отчет, ему тут не место)`.
- Имя файла, команды или поля пишется, только когда оно само и есть изменение (удалено,
  добавлено, переименовано), в обратных кавычках: `Удалены data_migrations.py и make fixtures`.
- Слова из кода не переводятся и не объясняются: сокет, ручка, фикстура, админка, свагер.
- Символы только с клавиатуры: `-`, `"`, `+`, `/`. Без `—`, `«»`, `→`, жирного и эмодзи.

Следов генерации быть не должно. Под запретом:
- вступления и итоги: "В этой ветке...", "Основные изменения:", "Таким образом"
- оценки: "значительно улучшен", "более надежный", "оптимизирован" без факта, что именно
- канцелярит: "осуществлен", "произведена", "в рамках", "с целью", "данный"
- пары и тройки ради ритма: "удобнее, быстрее и надежнее"
- пересказ имени коммита слово в слово, если из него не понять смысл

## Заголовок MR

`<тип>: <ЗАДАЧА> <суть>`, несколько задач через ` & `. Тип - по главному коммиту ветки
(`feat`, `fix`, `refactor`). Суть - одна фраза с маленькой буквы по смыслу задачи, без точки.
Задачи без номера в заголовок не идут.

```
feat: SHOP-275 новый статус заказа в уведомлении о его смене & SHOP-235 id заказа совпадает с id на складе
```

## Формат с несколькими задачами

Номер задачи с двоеточием, под ним список, пустая строка после каждого блока:

```
SHOP-273:
- Исправлена админка Users, теперь позволяет создавать пользователей
- Поля ФИО перенесены из Profile в Users модель
- Добавлена ручка импорта пользователей из .csv
- Обновлен маппер ошибок Pydantic
- Обновлена make команда на обновление фикстур

SHOP-248:
- Назначить курьера можно только NEW заказу
```

## Примеры

Одна задача, основное - что удалено:

```
- Старые роли переименованы под роли склада и курьера
- Удалена регистрация
- Удалена оплата картой
```

Крупная переделка с деталями и оговоркой:

```
- Переработка импорта/экспорта на интеракторы
- Статусы заказов вынесены на id + ручку-справочник (пока сохранен старый вывод)
- Ссылка в заказе показывается только если он доставлен + ведет на карту
- Обновлена система уведомлений
  - Уведомления теперь могут быть непрочитанными
  - Добавлено событие в сокет на пометку прочитанным
```

Рефактор, мелочь собрана в общие строки:

```
- Доработан пагинатор и GenericViewSet
- Выборка заказов вынесена в OrdersManager
- Код в целом приближен к Django style
- Свагер-схемы переведены на кортежи схем с custom_method_decorator (есть типовые ответы)
- Декомпозированы тесты сокетов
- Прогнан ruff + mypy с фиксом всего, на что они ругались
```

Ломающие изменения идут отдельными пунктами:

```
- Справочники автоматически синхронизируются с моделями
- Справочные модели закрыты для редактирования/создания в админке
- Удалены `data_migrations.py` и `make fixtures`
- Добавлен `make createadmin`, создающий admin/admin юзера
```
