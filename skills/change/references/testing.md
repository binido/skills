# Полезные тесты без раздувания набора

Применяй при добавлении и изменении тестов. Сохраняй обязательные проверки проекта.
Правила ниже задают отбор и структуру сценариев, дополняя TDD и другие скиллы.

## Сначала докажи необходимость

Перед написанием нового сценария определи:

1. Какое требование или реальную регрессию он защищает.
2. Какое ошибочное поведение заставит его упасть.
3. Почему существующие проверки это поведение не обнаруживают.

Если ответа нет, новый сценарий не нужен. Для небольшого изменения достаточно
короткого обоснования в плане; отдельный документ и согласование каждого теста
не требуются. Если подходящий тест уже есть, дополни его данные или проверки.

Проверяй наблюдаемый контракт через интерфейс, которым пользуется вызывающая
сторона. Изменение внутреннего устройства при сохранении поведения не должно
ломать тест. Тест алгоритма через интерфейс функции может быть полезен;
сам по себе формат unit-теста не делает проверку лишней.

Лишние проверки: чтение исходника ради совпадения строк, тривиальная инициализация
и присваивание без собственного контракта, повторение гарантий библиотеки,
ожидаемый результат, вычисленный копией проверяемого алгоритма.
Порядок и число внутренних вызовов проверяй лишь когда они выражают контракт,
например запрет повторного списания, а не выбранный способ реализации.

## Выбирай сценарии по риску

Используй минимальный набор, различающий существенно разные правила поведения:
требуемый успешный результат, существенный отказ и границы изменённого правила.
Для дефекта сохрани сценарий, воспроизводящий именно описанную ошибку.
Несколько значений с одинаковым смыслом не дают нового покрытия только за счёт
количества; другая граница, роль или переход состояния могут давать.

Одна проверка поведения может содержать несколько связанных утверждений:
например статус, значимые поля ответа и наблюдаемый эффект операции.
Не дроби её на отдельные тесты ради каждого `assert`. Не ограничивайся одним
статусом, если неверное содержимое или побочный эффект тоже нарушают требование.

Выбирай наиболее узкий уровень, который обнаружит нужный дефект. Проверка
бизнес-правила на уровне функции не подтверждает подключение этого правила
к HTTP-ручке; HTTP-тест не всегда заменяет точные проверки сложного алгоритма.
Добавляй второй уровень только для отдельного риска, который первый не ловит.

Общее поведение авторизации, 404 и пагинации проверяй в общей точке, если оно
уже покрыто и действительно одинаково. На конкретной ручке проверяй её особые
роли, владение объектом, фильтры и подключение защиты, когда ошибка возможна
именно там. Наличие теста middleware само по себе не доказывает защиту всех ручек.

Для правки текста, форматирования или чисто механического изменения используй
существующие проверки, если нового риска поведения нет. Для значимых расчётов,
доступа, сохранности данных и переходов состояния сохраняй необходимые проверки.
Количество тестов и процент покрытия не заменяют оценку риска. Соблюдай настроенный
порог покрытия; падение порога обозначь, а не обходи снижением настроек.

## Группируй по поведению

Принятое здесь правило для API-ручки: две отдельные параметрические функции,
положительная и отрицательная. Это предпочтение пользователя, а не стандарт pytest.
Число строк параметризации определяется нужными сценариями, а не квотой.
Самостоятельные контракты с другим устройством сценария требуют отдельных групп;
добавляй их только с обоснованием отдельного риска или по требованиям проекта.

- Объединяй варианты, у которых одинаковые подготовка, действие и смысл проверок;
  меняются входные данные и ожидаемые значения. В pytest используй `parametrize`,
  в другом стеке — аналогичную табличную форму.
- Успешные случаи и ожидаемые отказы разделяй. Не создавай общую функцию
  с флагом `is_valid` и ветками для разных способов проверки.
- Разные отказы можно объединить, если их проверки имеют одну форму. Если для
  части строк нужны другие фикстуры, действия или ветвления, раздели группы.
- Давай случаям понятные имена через `ids` или `pytest.param(..., id=...)`.
  Каждая строка — отдельный запускаемый случай; параметризация не оправдывает
  ненужные варианты и не уменьшает сама по себе время исполнения.
- Несколько декораторов параметризации создают произведение комбинаций.
  Используй явные нужные пары, если нет требования проверять все сочетания.

Параметризацию используй для однотипных вариантов. Единственный сценарий
самостоятельного поведения не требует искусственных дополнительных строк.
Предпочитай явные локальные данные универсальному генератору сценариев.

## Перед завершением

Проверь новые функции и строки параметризации на дубли и полезность по трём
вопросам выше. Для исправления ошибки покажи падение на старом поведении и
успех после исправления, когда воспроизведение доступно. Для новой фичи в TDD
используй тот же цикл; вне TDD проверь, что тест различает правильный и ошибочный
результат. Полный mutation testing для каждой задачи не требуется.

Не устраивай чистку всего набора тестов за пределами порученного изменения.
Уже существующие проверки удаляй или объединяй в рамках задачи и только если
сохраняется защищаемое поведение. Новые библиотеки, фикстурные слои и тестовые
frameworks добавляй лишь при необходимости, которую не покрывает окружение проекта.

Обоснование и первоисточники: [разбор рекомендаций](testing-research.md).
