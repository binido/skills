# /naturalise-text — Причёсывание текстов под человека

Аргументы: `$ARGUMENTS` — путь к файлу или пусто (тогда смотреть весь diff ветки).

Правила ниже — про русскоязычные тексты в любом проекте (API-описания, docstrings, комментарии, UI-строки). Конкретные поля/атрибуты, где искать такие тексты, зависят от стека — найди их на шаге 2, ориентируясь по смыслу (что попадает в документацию API, что видит пользователь), а не по конкретным именам ниже.

---

## Что считается AI-текстом

**Запрещено:**

- Двоеточие как разделитель разделов: `"Список: раздел А и раздел Б"` → заменить на `"Список с разделами А и Б"` или через тире
- Кавычки-ёлочки `«»` в API-описаниях и пользовательских строках. В сообщениях логов и служебных названиях — допустимо
- Вложенные перечисления: `"X (детали) и Y (детали). Данные получены из Z."` — это не человек
- Слова-маркеры: "конкретного X" (вместо просто "X"), "постраничный список", "данные реконструируются", "передайте X для Y"
- Длинные многосоставные описания с несколькими предложениями там, где соседние по смыслу места обходятся одним

**Эталон хорошего стиля** (нейтральный пример):
```
'Получение списка заказов с фильтром по диапазону дат и поиском по номеру.'
'Принимается только для заказа, ожидающего подтверждения.'
'Отмена заказа в статусе NEW или PROCESSING.'
'Заказы: список и фильтры'
```

## Алгоритм

1. **Собери scope:**
   - Если аргумент — путь к файлу, читай его
   - Если аргумент пустой, смотри `git diff <base>...HEAD` (только добавленные/изменённые строки); базовую ветку уточнить у пользователя или взять дефолтную ветку репозитория

2. **Найди AI-тексты** — искать по смыслу поля/места, которые видит человек или которые попадают в документацию API:
   - Описания ручек/операций для генерируемой документации API (swagger/OpenAPI-аннотации и т.п.)
   - Тексты в классах политик/прав доступа, если они выводятся пользователю
   - Docstrings в публичных методах контроллеров/обработчиков запросов
   - Docstrings в публичных методах бизнес-логики (входные точки сервисов/юзкейсов)
   - `help_text`/аналогичные атрибуты в схемах валидации
   - Комментарии `#`/`//` — только если они явно объясняют "что", а не "почему"

3. **Выведи находки** в формате:
   ```
   file.py:42  <поле/атрибут>
   ─ было:    'Список конкретных заказов: раздел «Активные» (детали) и раздел «Архив» (детали). Данные реконструируются из логов.'
   ─ стало:   'Список заказов с активными и архивными записями.'
   ```

4. **Примени все исправления** сразу — без лишних вопросов, если находок меньше 10. Если больше — спроси сначала.

5. **Запусти lint** на изменённых файлах — команду взять из `Makefile`/`package.json`/`CLAUDE.md` проекта.

## Правила замены

| Паттерн | Замена |
|---------|--------|
| `X: подраздел А и подраздел Б` | `X с подразделами А и Б` |
| `«слово»` в API-описании | убрать кавычки или переформулировать |
| `конкретного X` | просто `X` (контекст и так понятен) |
| `данные реконструируются из Y` | убрать — это внутренняя деталь |
| `постраничный список X (lazy scroll по Z)` | `список X с постраничной навигацией по Z` |
| `Передайте X из предыдущего ответа` | убрать — это уже описано в параметре |
| Два предложения там где соседи пишут одно | сократить до одного |

---

## Не трогать

- Текст внутри `«»` в пользовательских сообщениях об ошибках, в строках логов, в служебных названиях команд — это данные, не описания
- `# ponytail:` комментарии
- Docstrings с объяснением "почему" (нетривиальный инвариант, workaround) — даже если длинные
- Миграции, файлы с примерами данных (fixtures/JSON), тесты
