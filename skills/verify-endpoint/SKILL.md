# /verify-endpoint — Runtime-проверка ручек API на живом сервере

Аргументы: `$ARGUMENTS` — ручка и сценарии (тикет, ФР/ОР из баг-репорта, или свободное описание «проверь что...»).

Скилл не завязан на конкретный стек — все имена сервисов, портов, полей и таблиц ниже обозначены как `<плейсхолдеры>` и должны быть обнаружены из проекта на Шаге 0, а не предполагаться заранее.

---

## Принципы

1. **Только реальные HTTP-запросы.** Не симулировать внутренние объекты фреймворка (request/response, form-data) в изолированном Python — обёртки фреймворков часто ведут себя иначе, чем предполагает наивная симуляция (например, парсинг multipart отличается от обычного dict). Симуляция может показать баг, которого нет, и наоборот.
2. **Вердикт по фактическому ответу**, не по чтению кода. Текст ошибки в ответе говорит, *какой слой* её кинул (валидация на уровне схемы/сериализатора vs бизнес-логики обычно формулируется по-разному) — используй это, чтобы понять, какая из дублирующих проверок реально стреляет.
3. **Всегда минимум один негативный/граничный сценарий** сверх запрошенных: граница интервала, значение «ровно сейчас», пустая строка vs отсутствие ключа, лишнее поле.

---

## Шаг 0 — Разведка проекта и живость окружения

Прежде чем строить запросы, обнаружи специфику проекта:

- Как поднимается сервис: `docker-compose.yml`/`compose.yaml`, `Procfile`, `Makefile`, `README`, `CLAUDE.md` — имя контейнера/процесса, порт, base URL.
- Есть ли hot-reload у кода в контейнере (bind mount) или после правки файла нужен рестарт — смотри `docker-compose.yml` (`volumes:`) и логи после изменения файла.

```bash
docker ps --format "{{.Names}}: {{.Status}}"   # найти нужный контейнер, убедиться что Up
```

Если код монтируется в контейнер с автоперезагрузкой — после правки файла проверить, что контейнер видит новую версию:

```bash
docker exec <container> grep -n "<фрагмент нового кода>" <путь-в-контейнере>
docker logs <container> --since 1m 2>&1 | grep -iE "reloading|restart|error"
```

Промежуточная ошибка импорта/сборки между сохранением двух связанных файлов — обычно норма, самоустраняется после следующего reload. Убедись, что последний reload чистый.

## Шаг 1 — Авторизация

Найди ручку логина и формат payload в коде проекта (`grep -rn` по urls/routes на "login", "auth", "token", "session") вместо угадывания:

```bash
TOKEN=$(curl -s -X POST http://localhost:<port>/<auth-endpoint>/ \
  -H "Content-Type: application/json" \
  -d '{"<login-field>":"<user>","<password-field>":"<pass>"}' | python3 -c "import sys,json; print(json.load(sys.stdin)['<token-field>'])")
```

Подводные камни:
- Имя поля пароля/логина и URL ручки могут отличаться от «стандартных» (`password`, `/auth/login/`) — сверяйся с реальным сериализатором/схемой, а не с интуицией.
- Имя поля токена в ответе тоже нужно проверить (`access`, `token`, `jwt`, ...), и как он передаётся дальше (`Authorization: Bearer`, cookie, кастомный заголовок).
- У токена обычно есть TTL — при долгой сессии может понадобиться перелогин.
- Неизвестный URL? Если у фреймворка есть debug-режим — страница 404 часто перечисляет все зарегистрированные маршруты. Либо искать в файлах роутинга проекта.

## Шаг 2 — Доступы/права (если в проекте есть RBAC/policy-слой)

Проверь, включена ли проверка прав доступа (флаг в конфиге/settings/env). Если выключена — роль пользователя не важна для локальной проверки. Если включена — найди, какая роль/permission нужна нужной ручке, и либо выдай её тестовому пользователю, либо отключи проверку через конфиг окружения (только локально, не в шаренной среде).

## Шаг 3 — Тестовые данные

- Найди в проекте, какие сущности-предпосылки (ID существующих объектов, справочники) нужны для вызова ручки — обычно есть list/detail-ручка или консоль ORM, чтобы получить рабочий ID вместо выдумывания.
- **Файл для file-полей** (минимальный валидный PDF, в scratchpad-директорию сессии):

```bash
printf '%%PDF-1.4\n1 0 obj<</Type/Catalog/Pages 2 0 R>>endobj\n2 0 obj<</Type/Pages/Kids[3 0 R]/Count 1>>endobj\n3 0 obj<</Type/Page/Parent 2 0 R/MediaBox[0 0 3 3]>>endobj\nxref\n0 4\n0000000000 65535 f \ntrailer<</Size 4/Root 1 0 R>>\nstartxref\n0\n%%%%EOF' > "$SCRATCH/test.pdf"
```

- Если ручке нужны данные, которых нет в локальной БД (например, зависимые записи с внешними ключами) — засей их напрямую через SQL/ORM-консоль проекта. Порядок:
  1. Проверь, не отстаёт ли sequence/autoincrement от уже вставленных строк, если вставляешь с явным ID.
  2. Найди корректные значения для FK-полей в соответствующих справочных таблицах вместо произвольных.
  3. Вставляй минимально достаточный набор строк для прохождения нужного сценария.

## Шаг 4 — Прогон сценариев

Шаблон для multipart-ручек (JSON — обычный `-d` + `Content-Type: application/json`), адаптировать под реальные поля конкретной ручки:

```bash
req() {
  local label="$1"; shift
  curl -s -X POST http://localhost:<port>/<endpoint>/ \
    -H "Authorization: Bearer $TOKEN" \
    "$@" \
    -w "\nHTTP_CODE:%{http_code}\n"
}
req "сценарий 1" -F "field=value" -F "start=..." -F "end=..."
```

Даты на macOS: `date -u -v+1d +"%Y-%m-%dT%H:%M:00.000Z"` (`-v-2d`, `-v+2H` и т.п.); на Linux — `date -u -d "+1 day" +"%Y-%m-%dT%H:%M:00.000Z"`.

Стандартный чек-лист сценариев для полей с датами/дефолтами:
- ключ отсутствует; ключ = `''` (в некоторых фреймворках пустая строка в multipart трактуется как «не передано» для optional-полей — проверь в коде); валидное будущее; «ровно сейчас»; явное прошлое (и «сегодня, но раньше» отдельно — date-based и strict-валидаторы могут вести себя по-разному); `end==start`; `end<start`; граница интервала ровно N и N+чуть-чуть; лишнее поле, если у сериализации строгий режим; каждое обязательное поле по очереди убрать.

## Шаг 5 — Проверка вглубь

- **Логи после прогона** (нет ли скрытых 500-х):

```bash
docker logs <container> --since 5m 2>&1 | grep -iE "error|traceback|exception"
```

- **Побочные записи в БД/сторе** (что создалось/не создалось) — через ORM-консоль или SQL-клиент проекта:

```bash
docker exec <container> <shell-для-orm-консоли-проекта> -c "
<получить и распечатать записи, отфильтрованные по тестовой метке>"
```

- **Бизнес-логика напрямую** (если она используется/будет использоваться вне HTTP): собрать соответствующий сервис/юзкейс/интерактор руками через консоль проекта и вызвать его с граничными значениями — так можно отличить баг валидации от бага транспортного слоя.

## Шаг 6 — Отчёт

Формат: вердикт (PASS/FAIL/BLOCKED) → таблица/список сценариев с фактическими кодами и телами ответов → замечания (что удивило, потолки решения, расхождения слоёв валидации). Тестовые сущности, созданные в БД, перечислить (id) — чистить только если пользователь попросит.

## Известные грабли

- `curl` exit 26 → файл фикстуры пропал (scratchpad может чиститься между сессиями) — пересоздать.
- Debug-страницы 404 у некоторых фреймворков отдают огромный HTML — для незнакомых URL использовать `-o /dev/null -w "%{http_code}"` или сразу смотреть роутинг в коде.
- Тексты ошибок разных слоёв валидации (схема vs бизнес-логика) обычно различаются — по тексту в ответе определяй, какой слой сработал.
- Разные слои могут считать «одинаковую» проверку по-разному (например, интервал дат: разница в секундах vs разница календарных дат) — граничные сценарии гонять с расчётом на оба варианта.
- Команды сборки/lint/тестов — брать из `Makefile`/`package.json`/`CLAUDE.md` проекта, не выдумывать свои.
- Не коммитить: git-операции строго ручные, если явно не попросили.
