# Полезные тесты: основания для правил change

Исследовано 2026-10-04. Ниже первичные источники и отдельно — выводы для этого скилла. Это рекомендации по выбору проверок, а не универсальная квота тестов.

## Что рекомендуют источники

- **Проверять поведение через доступный потребителю интерфейс.** Рефакторинг с сохранением поведения обычно не должен менять проверки результата. Внутренние взаимодействия проверяют, когда они сами значимы: например, чтение из кеша вместо дорогого хранилища. Публичный интерфейс здесь может быть функцией или классом, не обязательно HTTP. [Google: Test Behavior, Not Implementation, Andrew Trenk, 2013](https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html).
- **Не переписывать реализацию в тест.** Проверка порядка внутренних вызовов без независимого требования может быть лишь детектором изменений: ломается после корректного рефакторинга, не доказывая правильность результата. Такие тесты предлагают переписывать или удалять. [Google: Change-Detector Tests Considered Harmful, Alex Eagle, 2015](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html).
- **Один тест — одно поведение, а не один метод или один assert.** В примере Google количество писем и тема письма проверяются вместе как одно поведение; уведомление о покупке проверяется отдельно. Несколько проверок одного результата допустимы. [Google: Test Behaviors, Not Methods, Erik Kuefler, 2014](https://testing.googleblog.com/2014/04/testing-on-toilet-test-behaviors-not.html).
- **Выбирать слой по дополнительной уверенности.** Не нужно повторять наверху все ветки, надёжно проверенные ниже. Интеграционный тест должен проверять то, чего нижний слой не доказывает: например, что HTTP-маршрут действительно подключён. Удаление дублей оправдано отсутствием добавочной ценности, а не одинаковым названием сценария. [Ham Vocke: The Practical Test Pyramid, 2018](https://martinfowler.com/articles/practical-test-pyramid.html).
- **Ясность важнее максимального устранения повторов.** Google рекомендует DAMP: тест должен содержать данные для понимания своего поведения. Умеренное повторение подготовки допустимо; сложные универсальные helpers, ветвления и общий валидатор всех свойств затрудняют диагностику. Регрессионный тест добавляют на пропущенный сценарий бага. [Software Engineering at Google, глава 12](https://abseil.io/resources/swe-book/html/ch12.html).
- **Coverage показывает пробелы, но не доказывает качество.** Высокое покрытие может соседствовать с плохими проверками и пропущенными границами. Тесты ради процента создают расходы на поддержку. Требуемое покрытие определяется рисками продукта; существующий порог CI всё равно является ограничением проекта. [Google: Code Coverage Best Practices, Carlos Arguelles, Marko Ivanković, Adam Bender, 2020](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html).
- **Права доступа заслуживают самостоятельных проверок.** OWASP рекомендует unit- и интеграционные тесты авторизации, включая отказ по умолчанию, соблюдение политик и безопасные отказы. Маленькая ошибка конфигурации может иметь серьёзные последствия. [OWASP: Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#create-unit-and-integration-test-cases-for-authorization-logic).
- **Параметризация не означает один исполняемый случай.** pytest собирает отдельные случаи; `ids` помогают назвать их. Несколько декораторов параметризации создают декартово произведение. Официальная документация допускает сочетание успешных вызовов и ожидаемых исключений через `nullcontext` и `pytest.raises`; их разделение ниже — пользовательская конвенция. Документация получена через Context7 для `/pytest-dev/pytest`. [pytest: Parametrizing tests](https://docs.pytest.org/en/stable/how-to/parametrize.html), [pytest: Parametrizing conditional raising](https://docs.pytest.org/en/stable/example/parametrize.html#parametrizing-conditional-raising).

## Выводы для политики change

Это применение рекомендаций к запросу пользователя, а не дословные правила источников.

1. Перед новым тестом назвать конкретное требование, регрессию или риск, который он ловит, и проверить существующее покрытие этого сценария. Предпочесть расширение подходящего теста новому дублю.
2. Не добавлять тест только потому, что появился метод, поле конструктора, тривиальный делегат или файл. Сначала определить нарушаемый контракт. Простой код всё же требует проверки, если ошибка значима или интеграционное подключение легко нарушить.
3. Параметризовать варианты одного сценария с общей подготовкой, действием и формой проверки. Не копировать тела ради смены входных данных. Не объединять разные сценарии ради уменьшения числа функций.
4. Если общая функция требует `if success`, разных действий, разных фикстур или разных наборов проверок для строк таблицы, разделить сценарии. Значение ожидаемого результата может отличаться без ветвления; само по себе это не основание для разделения.
5. Выбирать значения по различимым правилам и значимым границам, а не добавлять много произвольных примеров одинакового класса. Не разворачивать декартово произведение параметров, если взаимодействие комбинаций не связано с риском.
6. Несколько assert допустимы для одного контракта: например, успешное создание проверяет код ответа, поля результата и сохранённое состояние; отказ — код ошибки, причину и отсутствие записи.
7. Не запрещать unit-тесты или mocks целиком. Проверка взаимодействия полезна, когда отправка сообщения, транзакция, повтор или другой внешний эффект составляет требование. Изолировать дорогую или недетерминированную границу, а не подменять всю проверяемую логику.

## Предпочтения пользователя для API

Это локальные правила формы и объёма работы, не общепринятый стандарт «два теста на ручку».

- Положительные и отрицательные API-сценарии держать в **разных тестовых функциях**; внутри каждой параметризовать однородные варианты. Отдельные независимые поведения могут потребовать дополнительных функций. Не создавать пустую или искусственную группу ради квоты.
- При изменении задачи проверять затронутый контракт и связанные риски. Не превращать разработку одной фичи в написание тестов всех соседних ручек.
- Не повторять во всех ручках полную матрицу общей авторизации, общих 404 или механизма пагинации, **если** она проверена централизованно и новая проверка не добавляет уверенности.
- Сохранять проверки подключения защиты к маршруту, правил ролей, владельца и tenant, скрытия чужого ресурса, уникального поиска/404, фильтрации и стабильного порядка страниц. Общий middleware не доказывает правильность конфигурации и бизнес-правил каждой ручки.
- Не удалять старые тесты массово в рамках обычной задачи; упрощать затронутые дубли с сохранением сценариев. Не обходить проектный coverage gate ради сокращения числа тестов.

## Быстрый критерий перед добавлением

«Какое неверное наблюдаемое поведение сломает этот тест и почему существующие проверки его не ловят?»

Если ответ отсутствует, тест нужно пересмотреть. Если ответ есть, выбрать самый простой надёжный слой и ясную структуру; количество тестовых функций не является целью.
